# Tor の仕組み（ナレッジ）

`tor_mcp` がどうやって匿名で .onion / Web にアクセスしているのか、その土台に
ある **Tor の動作原理** をまとめたナレッジ。実装やトラブルシュート手順は
[../README.md](../README.md) を参照。

## 一言でいうと

> アプリは **SOCKSプロキシ** で tor に取り次ぎ、通信は **Torリレー網を3ホップ
> ・玉ねぎ暗号化** で通り、clearnet なら **出口ノード** から HTTP/HTTPS が、
> .onion なら **合流点（Rendezvous）** でエンドツーエンド暗号化が成立する。

「入口 = SOCKS / 中 = 特定ネットワーク / 通信 = HTTP(S)」というイメージは骨格
としては正しいが、以下の3点を押さえると正確になる。

## 1. SOCKS は「入口の取り次ぎ」だけ

SOCKSプロキシは「どこへ繋ぎたいか」を tor に伝えるための **ローカルAPI** に
すぎない。経路選択や暗号化を SOCKS がやっているわけではなく、それは tor が
独自プロトコル（固定 512 バイトの **Torセル**）で行う。

```
アプリ ──(SOCKS5h 127.0.0.1:9050)──▶ tor.exe ──(Torプロトコル)──▶ Torリレー網
```

- 本プロジェクトでは httpx が `socks5h://127.0.0.1:9050` で tor に接続する。
- `socks5h` の **`h`** は「**DNS解決も tor 側で行う**」の意味。ローカルで名前
  解決して宛先ホスト名を漏らさない（DNSリークを防ぐ）ため重要。

## 2. 本質は「3ホップの玉ねぎ暗号化」

通常、通信は **3つのリレー** を経由する。

```
あなた ─▶ [Guard 入口] ─▶ [Middle 中継] ─▶ [Exit 出口] ─▶ 目的のサーバ
```

- クライアントが宛先データを **3重に暗号化**（＝玉ねぎ Onion）してから送る。
- 各ノードは **自分の層だけ** を復号し、**次の1ホップ先しか知らない**。
  - **Guard** … 「あなた」を知るが、最終宛先は知らない。
  - **Exit** … 最終宛先を知るが、「あなた」は知らない。
- この「誰も全体像を持たない」構造で匿名性が成立する。
- Guard は固定されやすい（エントリガードの長期固定）など細部はあるが、原理は
  上記の通り。

## 3. HTTP/HTTPS は「中身」、Tor は「運び方」

Tor はあくまでトランスポート。中身が HTTP か HTTPS かは別レイヤ。

### clearnet（普通の Web）の場合
Exit ノードが目的サーバへ実際に TCP 接続し、そこから HTTP/HTTPS が流れる。

- **HTTPS でないと Exit ノードに中身を覗かれる**（改ざんも理屈上可能）。
  → clearnet を Tor 経由で扱うときは **HTTPS 必須**。
- 出口IPは Exit ノードのIP。`tor_check` が返す `exit_ip` がこれ。
  `tor_new_circuit` で別の Exit に変えられる。

### .onion（Hidden Service / Onion Service）の場合
clearnet とは別物。Exit ノードを通って「外」に出ない。

- クライアントとサービスが **Rendezvous Point（合流点）** で落ち合う方式。
  → **Exit が存在しない**＝Tor網の外に出ないので、出口での盗聴面がない。
- `.onion` アドレスは **サービスの公開鍵から導出** される。よって TLS が無くても
  アドレス自体がエンドツーエンドの暗号化・認証を担保する。

## まとめ図

```
[clearnet]
 あなた ─玉ねぎ3層─ Tor網 ─ Exit ── HTTP/HTTPS ──▶ example.com
                                     ^ HTTPSでないと覗かれる

[.onion]
 あなた ─玉ねぎ─┐                        ┌─ サービス
                └─▶ Rendezvous Point ◀─┘
                     （双方が合流／Exitなし・E2E暗号化）
```
